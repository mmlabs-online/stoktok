# Plan — STK-084: Register stoktok on the shared Postgres, move data from Supabase, cutover and docs (slice A1: stoktok code, deploy drafts and docs)

This plan covers **slice A1 only**: changes in the stoktok repo, merged to main with **no release cut**. The data-move script, the cutover runbook, both deployment-repo PRs, the cutover itself and the contract step are follow-up tickets (see `## Split proposal`).

## Spec summary
- ticket.md Goal: "Add `/readyz` (DB ping) if the deploy health check needs it." "`deploy-stoktok.yml` writes `STOKTOK_DATABASE_URL=postgres://stoktok:<pw>@postgres:5432/stoktok` from `postgres/secrets/apps/stoktok.password` (plus the AI master key) into the host env file, takes a pre-migration dump via `pg-backup /backup.sh`, runs `migrate` before replacing the app". "CLAUDE.md Stack (DB row; OrbStack on an Intel Mac instead of WSL2), Conventions (secrets); spec §7 diagram, secrets line and risks row (Supabase Free pausing accepted)."
- ticket.md "Shared-Postgres standard": "`postgres:17`, reachable only as `postgres:5432` on the external Docker network `db`". "The deploy workflow writes the URL into the host env file from the committed password file (no GitHub secret). stoktok keeps the env name `STOKTOK_DATABASE_URL`". "Migrations: a one-shot `migrate` compose service, run by the deploy after a pre-migration dump (`pg-backup /backup.sh`) and before the app is replaced; a failed migration leaves the old release running."
- ticket.md "Release rule": "no stoktok release is cut until STK-084; production stays on the current Supabase-backed release until the cutover."
- ticket.md AC 3 (part in this slice): "wire the deploy workflow and `check-deploy-env.sh` (required, format `^[A-Za-z0-9+/]{43}=$`), switch its `docs/deploy.md` row from `reserved` to required, host env file mode 0600."
- ticket.md notes, 2026-11-11 (STK-083 F2): "`idle_in_transaction_session_timeout` set in `pg/client.ts` session init or the deployment repo DB config, not a migration"; (F3) "update the CLAUDE.md Stack DB row and 'Migrations in `supabase/`'".
- ticket.md notes, 2026-11-17 (STK-089 security review): "decide whether an exit-0 `migrate` when the database is AHEAD of the image (warning only) should block replacing the app during deploy."
- ticket.md notes, 2026-11-17 (Ming): "(1) the orchestrator may create branches and open the deployment-repo PRs itself (B: `add-app-db.sh stoktok` registration; C: the expand step that adds `STOKTOK_DATABASE_URL`, the master key and the `db` network while keeping `SUPABASE_*`) ... (2) Rollback window 14 days: `SUPABASE_*` stay in the env file during the window ... (3) After the window, keep the Supabase `public` tables as a read-only archive; delete only the old Vault AI keys."
- CLAUDE.md R3 (DB URL server-only, read only in `packages/db/src/pg/client.ts`), R6 (public list `/login` and `/healthz`; every other route calls `requireUser()`), R8.

## Decisions taken in this plan (open questions from the consults)
| # | Question | Decision | Why |
|---|---|---|---|
| D1 | `/readyz` semantics | `GET /readyz`, public (in `PUBLIC_PATHS`, no `requireUser()`), runs `select 1` through the web pool via a new `pingDb(db)` repo function, bounded by a 2 000 ms timer. 200 `{"status":"ok"}` or 503 `{"status":"unavailable"}`, `cache-control: no-store`. No version, no error text, no host in the body; a failure logs only `{"event":"readyz_db_unavailable","code":<DataError code or "config">}`. `/healthz` is unchanged (liveness, no DB). | Architect F4/R1-A, data-engineer risk "first release with a wrong DB URL". The host is behind Cloudflare Access, but the body is still minimal. |
| D2 | Version-agnostic health check | **No fallback.** The compose health check stays on `/healthz` in the expand PR (C); the cutover release-PR commit (D) switches it to `/readyz` together with adding the `migrate` service. | A fallback "try `/readyz`, else `/healthz`" has to treat 404 **and** 3xx as "old image" (v0.2.1 redirects `/readyz` to `/login` because it is not public there, and `fetch` follows redirects to a 200). A misconfigured new image (missing `PUBLIC_PATHS` entry) fails in exactly that way, so the fallback would hide the failure `/readyz` exists to catch. D needs a release-PR commit for `migrate` anyway (architect F3), so the switch adds no new manual step. |
| D3 | Idle-in-transaction timeout values | New pool-profile field `idleInTransactionTimeoutMs`: **web 30 000**, **worker 60 000**, set in the existing `set_config` session-init statement in `client.ts`. Not a role setting, not a migration. | DB consult §10 and architect R6. Transactions only wrap DB statements (`upsert.ts:101`, `data-gaps.ts:58`), so 60 s leaves a wide margin for chunked upserts. The runner uses its own client and is not affected. |
| D4 | Schema-diff in the dry run | **Mandatory in the dry run, informational (non-blocking) at the real cutover.** Recorded here for STK-091, which implements it. | Architect R2.1 says mandatory; DB consult §11 says it is cheap but the restore already fails loudly. A dry-run check costs nothing and shows Studio drift before the real move; the cutover itself does not wait on it. |
| D5 | "Database ahead of the image" | **Does not block** replacing the app. `migrate` keeps exit 0. The deploy draft captures the migrate output, emits a `::warning::` annotation and sets an `ahead=true` step output, which adds a suffix to the PR comment. The prefix is pinned by an exported constant `MIGRATE_AHEAD_PREFIX` in `packages/db/src/pg/migrate.ts`, a test-db assertion, and a `check-deploy-env.sh` check that the draft workflow contains the same literal. | DB consult §12, architect R4/F10: "ahead" is the designed state after a revert or rollback; blocking it would make a one-click revert impossible during an incident. The data-engineer's "block" view is rejected for that reason; visibility covers the concern. |
| D6 | B and C inside this plan? | **Split out** into STK-092 (B) and STK-093 (C). Slice A1 updates the drafts under `deploy/deployment-repo/` to the exact expand state, so C becomes "copy the reviewed drafts". | Different repo, different PR, different checks (stoktok's `typecheck`/`lint`/`test` do not run there), and the `/run` loop ends a ticket with one PR into stoktok `main`. C must be cut from drafts that already passed review here, so it is sequenced after A1 anyway. B has no dependency and can run in parallel. |

## Approach
1. **Idle timeout (D3).** Add the field to `PoolProfile` and both profiles; extend the `client.ts` `set_config` statement with `$3 = String(p.idleInTransactionTimeoutMs)`. Fail-closed behaviour of session init is unchanged. Tests as listed.
2. **`pingDb` and `/readyz` (D1).** `repos/health.ts` uses `q()` (S5 rule). Route: `export const dynamic = 'force-dynamic'`; `try { await Promise.race([pingDb(getDb()), timeout(2000)]) }` with the timer cleared in `finally`; 200 or 503 as in D1. Log only the event and a code (`DataError.code`, `'timeout'`, or `'config'`), never `e.message` (it can carry host or credentials, R3). Add `/readyz` to `PUBLIC_PATHS`, the R6 entry-point exemption, and the CLAUDE.md R6 note (R6: the public list is a rule the reviewer enforces, so the note must list it).
3. **Ahead prefix (D5).** Export the constant and use it in the existing `log(...)` call so the printed text stays byte-identical. No barrel export needed.
4. **Draft compose (expand state).** `stoktok-web`: `networks: [tunnel, db]`. `stoktok-worker`: `networks: [default, db]` (`db` is `--internal`: without `default` the worker loses egress to TCBS/VCI/RSS; architect F2). Declare `db: { external: true, name: db }`. Health check unchanged (`/healthz`, D2). No `migrate` service (architect F3: v0.2.1 has no `migrate` subcommand). Header comment: the env file now also holds `STOKTOK_DATABASE_URL` and `STOKTOK_AI_KEYS_MASTER_KEY`; the `migrate` service and the `/readyz` health check are added in the cutover release PR (STK-094). Do not write `NAME=` with a value pattern in comments (see step 6 guard).
5. **Draft workflow (expand state).** Follow `deploy-tudocuatui.yml:89-200` where it fits:
   - `env:` adds `DB_APP: stoktok`.
   - `secrets` step: add `STOKTOK_AI_KEYS_MASTER_KEY: ${{ secrets.STOKTOK_AI_KEYS_MASTER_KEY }}` to the step env; a `missing` line `[ -n "$STOKTOK_AI_KEYS_MASTER_KEY" ] || missing="$missing STOKTOK_AI_KEYS_MASTER_KEY"`; `re_master_key='^[A-Za-z0-9+/]{43}=$'` and `if ! [[ "$STOKTOK_AI_KEYS_MASTER_KEY" =~ $re_master_key ]]; then ... exit 1` before `mktemp`. Then `pwfile="postgres/secrets/apps/$DB_APP.password"`, `if ! grep -Eq '^[A-Za-z0-9_-]{16,}$' "$pwfile"; then ::error (names the file, not its content) ... exit 1`, `read -r pw < "$pwfile"`, `STOKTOK_DATABASE_URL="postgres://$DB_APP:$pw@postgres:5432/$DB_APP"` (a builtin assignment: no argv, no echo). All `SUPABASE_*`, `AUTHEN_*` and AI-key handling stays exactly as it is (Ming 2026-11-17 (2): the Supabase values stay during the window). The single `printf` writes `STOKTOK_DATABASE_URL=%s` first, then the existing keys, then `STOKTOK_AI_KEYS_MASTER_KEY=%s`, arguments in the same order. `chmod 600` and the owner/mode check stay.
   - New `pull` step (`if: steps.release.outputs.skip != 'true'`): `config --quiet` and `pull` with `--profile jobs --profile migrate`; output `migrate=true|false` from `config --services | grep -qx migrate`, with a `::notice::` when false.
   - New `backup` step (`if: steps.pull.outputs.migrate == 'true'`): `docker compose -p postgres -f "$HOME/srv/postgres/compose.yml" exec -T pg-backup /backup.sh`; failure → `::error::` "nothing was migrated or replaced".
   - New `migrate` step (same guard): step env `AHEAD_PREFIX: 'warning: database is ahead of this image'`; run `"${compose[@]}" run --rm migrate` with output captured (`set +e`, `out=$(... 2>&1)`, `rc=$?`), print it (the runner never prints the URL, `migrate.ts:1-4`), non-zero → `::error::` "the old release is still running" and exit 1; on `*"$AHEAD_PREFIX"*` → `::warning::Database is ahead of this image: nothing was migrated (expected after a revert or rollback).` and `ahead=true` output. Exit 0 in that case (D5).
   - `deploy` step: drop its own `config`/`pull` lines; `if: steps.pull.outcome == 'success' && (steps.pull.outputs.migrate != 'true' || steps.migrate.outcome == 'success')`; keep `up -d --wait --wait-timeout 120` and the recreate logic.
   - `rollback`, `publish`, `agent` unchanged (rollback never migrates).
   - `notify`: add `MIGRATE` and `AHEAD` env; `migrate:failure` → "migrate-failed: migrations for `$IMAGE` failed; the old release is still running. A dump was taken just before."; when `AHEAD=true` append "Database is ahead of this image (nothing migrated)."
   - Header comment: replace "No migrate step ..." with the TuDo-style numbered flow and the guard note; list `STOKTOK_AI_KEYS_MASTER_KEY` and the derived URL.
6. **`check-deploy-env.sh` rewrite** (architect R5). Keep every existing check that still applies; change:
   - Status set: `required now`, `optional`, `reserved`, `derived`. Only `STOKTOK_DATABASE_URL` may be `derived` (any other derived key → FAIL "unknown derived key").
   - Secret name map: `secret_of K` = `K` if `K` starts with `STOKTOK_`, else `STOKTOK_K`. Use it for the step-env mapping check and the `missing` line check of `required now` keys. Derived keys must have **no** `secrets.` mapping, and the workflow must contain `DB_APP: stoktok`, the `pwfile=` line, the `grep -Eq '^[A-Za-z0-9_-]{16,}$' "$pwfile"` guard, `read -r pw < "$pwfile"` and the `STOKTOK_DATABASE_URL="postgres://$DB_APP:$pw@postgres:5432/$DB_APP"` assignment, all inside the secrets step before `mktemp`.
   - Format guards: optional keys keep the exact `^[A-Za-z0-9._-]*$` guard check; `STOKTOK_AI_KEYS_MASTER_KEY` must have `re_master_key='^[A-Za-z0-9+/]{43}=$'` and `if ! [[ "$STOKTOK_AI_KEYS_MASTER_KEY" =~ $re_master_key ]]; then` with `exit 1` within 4 lines, before `mktemp` and the `printf`.
   - The env-file `printf`: identify it as the one line in the secrets step matching the existing `printf_shape` regex (no longer `grep -F "printf 'SUPABASE_URL="`); exactly one; its keys equal `required now + optional + derived`; format order equals argument order. Replace the `printf .SUPABASE_URL=` anchor in the awk guard and in `other_writers` with that line.
   - Env-writer location guard: none of `SUPABASE_SERVICE_ROLE_KEY=`, `STOKTOK_DATABASE_URL=`, `STOKTOK_AI_KEYS_MASTER_KEY=` appears under `deploy/deployment-repo/apps/stoktok/`.
   - Compose: `${...}` interpolation limited to `DEPLOY_ONLY` (tightened from "any .env.example key"); external network `db` declared; `stoktok-web` networks contain `tunnel` and `db`; `stoktok-worker` networks contain `default` and `db` (parse the two service blocks with `sed -n '/^  stoktok-web:/,/^  [a-z]/p'` or awk; bash 3.2-safe, no `mapfile`).
   - Step order list: `preflight release envdir secrets pull backup migrate deploy publish rollback agent notify`. `backup` and `migrate` carry `if: steps.pull.outputs.migrate == 'true'`.
   - Ahead prefix: extract `MIGRATE_AHEAD_PREFIX` from `packages/db/src/pg/migrate.ts` with `sed`; FAIL if empty or if the draft workflow does not contain `AHEAD_PREFIX: '<literal>'`.
   - The `.env.example` vs doc and `release.yml` DEPLOY_ONLY checks are unchanged.
7. **`release.yml`.** PR body: "Deploys `…` and `…` (commit link). Merging runs deploy-$APP on macbook-runner: a pre-migration backup and `migrate` (when apps/$APP/compose.yml has a migrate service), then the new app. Every migration must work with the previous image." No other change (the commit-scope guard stays).
8. **Docs.** `docs/deploy.md` as in the files table, including the new statuses: `derived` = "written by `deploy-stoktok` from a committed file in the deployment repo, not a secret of the environment". "Cut a release" step 1 becomes "Migrations run in the deploy (backup, then `migrate`); every migration must work with the previous image (expand, then contract)."
