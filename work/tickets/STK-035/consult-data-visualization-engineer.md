All ppm to percent conversion, sorting, and date comparison must therefore live in core or `lib/*.ts`.

## Recommendations

**A. Core view model (R1, AC2/AC3).** Add a pure `packages/core/src/signals/present.ts`:
1. `signalVisibility({signalDate, expectedDate, gaps, holidays, windowBounds}) -> {visible: true} | {visible: false, reason: 'behind_expected' | 'gap_overlap', lastSignalDate}`.
   - Stale means `signalDate < expectedDate`, or an open gap (this symbol or market-wide) overlaps the window. Reuse `gapOverlaps` and `vnDayBounds` from inputs.ts. Window per rule: the MA days, or the financials period for valuation and growth rules. If the window isn't derivable from the stored row, use the rule's price window from config (R5), not a magic number.
   - Decide the group, not each row: if the newest signal date across the symbol is stale, the whole medium-term block is hidden. Rows that individually have an overlapping gap are hidden. Return lastSignalDate = max signal_date that exists (null if none).
2. `presentSignal(row, ctx) -> SignalRowVM` with: `ruleName` (label map keyed by rule_id, `price_vs_ma_N` handled by pattern, with a safe fallback to the raw id plus "(quy tắc chưa có nhãn)" so an unknown rule never crashes), `direction` (`'bullish'|'bearish'|'neutral'`), `valueText` (core-formatted, e.g. "+12,4% so với trung vị ngành", "cao hơn đường MA50 3,2%", "3 quý tăng liên tiếp"), `signalDate`, `inputs: {ref, kind, source?, fetchedAt?, window?}[]`, `reasons: {code, text, kind: 'data'|'rule'}[]`. Parse `inputs_snapshot` defensively (zod or manual guards), since it's jsonb: malformed refs become "Không đọc được dữ liệu đầu vào" rather than throwing.
3. `REASON_LABELS: Record<ReasonCode, string> satisfies` exhaustive, plus a unit test that iterates `REASON_ORDER` and asserts a non-empty Vietnamese string with no code leakage (no underscores) and that no label contains an action word (mua/bán/nên). Same test for DIRECTION_LABELS.
4. Suggested Vietnamese copy (all neutral, directional, never advice):
   - Direction: bullish "Xu hướng tích cực", bearish "Xu hướng tiêu cực", neutral "Trung lập".
   - Reasons (data): price_missing "Chưa có giá", price_stale "Giá chưa cập nhật", insufficient_history "Chưa đủ lịch sử giá", price_gap / price_gap_recorded "Thiếu dữ liệu giá trong kỳ tính" / "Có khoảng thiếu dữ liệu giá đã ghi nhận", financials_missing "Chưa có báo cáo tài chính", financials_stale "Báo cáo tài chính chưa cập nhật", financials_gap(_recorded), financials_fetch_stale "Dữ liệu tài chính lấy về đã cũ", sector_missing "Chưa có thông tin ngành".
   - Reasons (rule): eps_basis_unverified "Chưa xác minh cách tính EPS", eps_non_positive "EPS không dương nên không tính P/E", bvps_non_positive "BVPS không dương nên không tính P/B", peers_insufficient "Không đủ mã cùng ngành để so sánh", value_out_of_range "Giá trị nằm ngoài khoảng hợp lệ", corporate_action_in_window "Có sự kiện quyền trong kỳ tính (giá chưa điều chỉnh)", price_jump_beyond_limit "Giá biến động vượt biên độ ngày, nghi ngờ dữ liệu chưa điều chỉnh".

**B. Visual structure of the section (placement: left column under the chart, before Position, on md+; on mobile order is Header, Chart, Position, Lots, Signals, Transactions, Disclaimer as in the STK-016 consult).**
- `<section aria-labelledby>` with h2 "Tín hiệu trung hạn". A one-line subtitle: "Tín hiệu theo quy tắc từ dữ liệu đã lưu, ngày tín hiệu dd/mm/yyyy".
- Render rows as a `<ul>` of cards on all widths (not a table): rule name + direction on line 1, value on line 2, meta (date, freshness) on line 3. Cards avoid the horizontal scroll a 5-column table needs at 375px. Rows ordered by a fixed core order (valuation, MA ascending, growth) so the list doesn't reshuffle between days.
- Direction badge must carry glyph + text, never color alone: ▲ Tích cực, ▼ Tiêu cực, ■/– Trung lập (reuse the TONE_STYLES approach but do NOT use up/down market green/red semantics blindly: a "bearish" on a price rule is a direction, not a loss. Use the existing up/down tones only with the glyph + sr-only prefix "Hướng:"; neutral tone for neutral). Avoid the words "Mua/Bán/Khuyến nghị/Nên" anywhere (R9/R10, AC1).
- Value: right-aligned only on desktop, left on mobile; use `tabular-nums`. Units spelled out in the text ("so với trung vị ngành"), because the same integer means different things per rule.
- Inputs: per-row `<details><summary>` "Dữ liệu đầu vào (n)" with `min-h-11` summary (44px target). Inside, a `<dl>` or compact `<ul>` per ref: kind label (Giá đóng cửa / Báo cáo tài chính / Khoảng thiếu dữ liệu), the period or date derived from the ref id by a core parser (not by string-splitting in the .tsx), "Nguồn: X", "Cập nhật: dd/mm/yyyy HH:mm". Gap refs show "Từ dd/mm đến dd/mm" with no source line. Price refs for an MA window may be 20-200 entries: collapse them into one summary line ("200 phiên, từ dd/mm đến dd/mm, nguồn: X, cập nhật mới nhất ...") rather than listing each. Core should compact refs by (kind, source) with from/to and the newest fetchedAt, while keeping the full list available in a nested "Xem từng bản ghi" `<details>` for audit. At 375px long ref ids need `break-all`/`overflow-wrap:anywhere`, and rows use a stacked layout.
- `<details>` is keyboard operable natively; verify the summary has a visible focus ring.

**C. Hidden/stale state (AC2).**
- Replace the whole list with one notice block (not hidden silently): `role="status"` is NOT needed (static, server-rendered); use a bordered warn-style panel with AlertTriangle icon + text: "Tín hiệu tạm ẩn do dữ liệu chưa cập nhật". Under it: "Tín hiệu gần nhất: dd/mm/yyyy" (or "Chưa có tín hiệu nào được lưu" when null), plus the specific cause in words ("Giá mới nhất là dd/mm, cần dữ liệu đến dd/mm" or "Có khoảng thiếu dữ liệu giá từ dd/mm đến dd/mm"). Do not render stale direction/value anywhere, not even greyed or in the table fallback, which would invite acting on old data.
- Warn color must come from the existing contrast-tested tokens (`text-warn`, as DataFreshnessBadge); icon + text carries the meaning.
- Distinguish three empty cases explicitly, each its own copy: (1) no signals ever stored (EmptyState "Chưa có tín hiệu cho mã này"), (2) stale/gap-hidden (above), (3) fresh but every row suppressed (show the suppressed rows, plus one summary line only if all reasons are data reasons).

**D. Suppressed rows (AC3).**
- Visible rows only, muted: rule name, a neutral "Tạm ẩn" chip with an icon (EyeOff / dash), no direction and no value (the DB check guarantees null, but the VM should enforce it too). Then reasons as a list of short sentences from `REASON_LABELS`, not joined into a single comma string, so screen readers read them as a list.
- Two styles: data reasons (warn icon, same family as DataFreshnessBadge), rule reasons (neutral, info icon, wording "Quy tắc chưa áp dụng được"). Both must still be legible without color (icon + text prefix).
- Suppressed rows still list inputs in the same `<details>` (e.g. the gap that caused it), because that is the explanation.
- Sort suppressed rows after ok rows within the list, keeping the fixed rule order inside each group, and include count in the h2 area: "3 tín hiệu, 2 tạm ẩn".

**E. Disclaimer (AC4).**
- Put `DisclaimerNote` directly under the signals section (inside it, after the list or the hidden notice), so it is adjacent to the content it qualifies and shown in all three states, including empty and hidden. Do not rely on a single page-bottom one only (on mobile the page is long and the footer is far from the signals). It's acceptable to also keep one at page end if the page already has one (it currently doesn't). text-xs is on the small side; on mobile use `text-sm`/at least 12px with the same muted token and confirm contrast with `contrast.test.ts` tokens. The text constant stays `DISCLAIMER_TEXT` (spec §2.3 wording), don't paraphrase.

**F. Mobile 375px.**
- Single column, rows are full-width cards, no horizontal scroll anywhere in the section (assert no table in the section; the chart already has its own scroll region). Min target 44px for every `<summary>`. Direction badge wraps beneath the rule name when the name is long ("Giá so với đường trung bình 200 phiên"). Dates in `dd/mm/yyyy` via formatDate.
- Avoid a sticky/side-by-side layout for md: left column is chart + signals, right column is position/lots/transactions (current grid is `md:grid-cols-2` with position left and transactions right; put Signals as a full-width row below the chart or in the left column; I recommend a full-width row between the chart and the two-column grid so the long details lists don't skew column heights).

**G. Accessibility.**
- Heading hierarchy: page h1 (symbol) / h2 sections / rule names as h3 inside `<li>` (or `<strong>` if headings get noisy; choose h3 so rotor navigation works).
- Direction announced as text: sr-only "Hướng:" is not needed when the visible text already says "Xu hướng tích cực"; glyphs `aria-hidden`.
- `<details>` summaries: describe what they open ("Dữ liệu đầu vào của P/E so với ngành, 3 mục") via the visible text; avoid an `aria-label` that differs from visible text (WCAG 2.5.3 label-in-name).
- Dates as `<time dateTime>` where cheap; fetched_at includes time zone context ("giờ VN") once in the section footer, not per line.
- Reduced clutter: no tooltips, no hover-only information (touch + keyboard). No charts in this ticket; do not add a sparkline per signal (no encoding gain, and the PriceChart already shows the series).
- Tests (component render, as `symbol-detail.test.tsx`): ok row shows label/value/inputs with source and fetched_at; hidden state shows last signal date and no direction text; suppressed row shows each Vietnamese reason and no raw code; forbidden-word scan (`/mua|bán|khuyến nghị|buy|sell/i` against direction labels and reason labels, excluding the disclaimer's "khuyến nghị đầu tư"); disclaimer present in all three states; `no-calc-in-ui` still passes.

**H. `listLatestSignals` (db read).** Signature like `listLatestSignals(db, symbol) -> StoredSignal[]` returning the newest row per `rule_id` (use a `signal_date desc` ordered select limited to the symbol, then dedupe by rule_id in the accessor, or `distinct on (rule_id)` via rpc; with a single symbol, rule count is small, so fetching the last N days and deduping is fine). Map `value` bigint to a number safely (JSON from PostgREST may give number or string; assert `Number.isSafeInteger`). Validate `status/label/reason_codes` shape, and map unknown reason codes to a catch-all label rather than failing the page (rule versions can add reasons faster than the UI deploys). Tests: newest-per-rule selection, other symbols excluded, empty, malformed inputs_snapshot. Server-only (R3).

## Risks
- Showing stale signals "greyed out" would be the main honesty failure; the model above forbids it. The expected price date is computed at request time, so a page viewed Monday morning before the cutoff uses Friday as expected: verify `expectedPriceDate` semantics so signals don't flicker hidden every morning before the worker runs; consider showing the "last signal date" with a softer message when the delay is just the cutoff window (open question 1).
- `inputs_snapshot` is untyped jsonb and size up to 32 KB. Rendering 200 price refs per MA rule x 3 MA rules on a mobile page is heavy DOM and unreadable; compaction in core is needed.
- Gap refs lack source/fetched_at, so AC1 "each cited ref shows source and fetched_at" cannot literally hold for them. Agree a rule: price/financials refs must show both; gap refs show interval only.
- Label wording: "tích cực/tiêu cực" for valuation rules can read as a recommendation (low P/E vs sector = "tích cực" may be read as "buy"). Prefer rule-specific neutral phrasing in valueText ("P/E thấp hơn trung vị ngành 12%") and keep the badge generic.
- Duplicate meaning of market up/down colors: a green "bullish" badge next to a red price change on the same screen can contradict. Use glyph+text and keep badge color neutral/low-saturation, or only tint through the existing tones with the text.
- Adjusted vs raw price: `corporate_action_in_window` and `price_jump_beyond_limit` are the guard for raw prices; the chart caption already states "chưa điều chỉnh", keep the wording consistent with the reason label.
- R6 suspended: the signals read exposes data publicly until go-live, same note as STK-018.

## Open questions
1. Hidden threshold: strictly `signal_date < expectedDate`, as the AC says? Before the daily worker run on a trading morning that hides everything. Confirm that is intended and that the cutoff (DEFAULT_PRICE_CUTOFF_MINUTES_VN) is the grace.
2. Window for the gap-overlap test: per rule from config (MA days / financial period) or one fixed window? Where does core get it from the stored row (rule_id + rule_version only)?
3. May the UI show ok-rows of rules that are fresh while others are stale, or is hiding all-or-nothing per symbol? (I recommended per-row for gap overlap and whole-block for date staleness.)
4. Rule name labels: are they config (R5) or a core constant? Need a decision for `price_vs_ma_N` and future rules.
5. Value display precision: percent with 1 decimal OK for ppm? Who owns the rounding rule (R2) in core?
6. Should refs for price windows be compacted (my recommendation) or listed in full to meet the AC literally?
7. Does the page show the section when the symbol is held and when it is only watched? (Assumed: always.)
