# STK-074 consult — data-visualization-engineer (UI)

## Findings
- /settings page (apps/web/app/(app)/settings/page.tsx) renders `<h1>`, then `AiUsageCard` (server, read-only, `max-w-2xl`, `aria-labelledby`), then `SettingsForm`. `SettingsForm` is ONE `<form max-w-2xl pb-24>` with all cards inside plus a sticky Lưu/Hủy bar. It uses `startTransition(() => formAction(fd))` with `useActionState`, and returns `null` when `state.ok`. After a successful save the action calls `redirect('/settings?saved=1')`.
- Card pattern: `bg-surface border-border space-y-4 rounded-lg border p-4`, `<h2>`, `text-fg-muted text-xs/sm` note. Shared helpers in components/transactions/form-fields.tsx: `inputClass`, `primaryButtonClass`, `Field`, `describedBy`, `FormBanner`. HolidayCalendarCard uses `min-h-11` buttons, `role="alert"` errors in `text-price-down`, and `role="status"` for notices.
- Actions pattern (settings/actions.ts): `'use server'`, `requireUser()` first, then a handler in `server/...`.
- figma-make-prompts.md has no key UI. Its generic rule (line 114) is that delete asks for confirmation in an AlertDialog. No dialog component exists in the settings code that I read.

## Recommendations
1. **Placement (AC1).** Put the card directly after `AiUsageCard` and before `SettingsForm`, as a sibling OUTSIDE the settings `<form>`. HTML forbids nested forms, and a key paste must not be submitted or reset by "Lưu thay đổi" or "Hủy". Use `max-w-2xl`. The two AI cards then sit together: spend, then keys. The key card gets its own `<form>` per provider row, with independent state and its own save/delete buttons. Do not put it in the sticky-bar form.
2. **Component.** Add `components/settings/ai-keys-card.tsx` ('use client'). The page (server) passes only non-secret rows: `{ provider: 'anthropic'|'google', label, status: 'unset'|'ui'|'env', last4?: string, savedAt?: string(ISO) }`. The server computes the status and last4. The client never receives the key and never receives env contents. Format the saved date in vi-VN, Asia/Ho_Chi_Minh, via the existing core/format helper. No money math is involved (R1).
3. **Row layout.** Each row is `<li>` or `<section aria-labelledby>` with the provider name (Anthropic, Google AI), a state badge, and controls. Rows stack on mobile and sit side by side on `sm:`.
4. **Input.** `type="password"`, `autoComplete="new-password"` (the reliable way to stop password-manager autofill), `autoCapitalize="off"`, `autoCorrect="off"`, `spellCheck={false}`, `inputMode="text"`, plus `data-1p-ignore`, `data-lpignore="true"` and `data-bwignore`. Use a unique `name` and `id` per provider, e.g. `key-anthropic`. Give it a visible `<label>`. Placeholder is a generic hint ("Dán khoá API"), never a sample key and never masked dots implying a stored value. Do not use a controlled `value` where an uncontrolled input with a ref works. If it is controlled, keep the value only in local state, never in the URL, a hidden field, or action state.
5. **Submit.** Use `useActionState` with the repo's `startTransition` + `onSubmit preventDefault` pattern, or a plain `<form action>`, since resetting the input on success is desired here. The state returned by the action must be `{ ok, message?, fieldError? }` only, with no `values` echo. Settings-form returns `values` to repopulate; do NOT copy that here (AC1 "never returned"). After success, clear the input explicitly (`formRef.reset()` or `ref.value=''`) and call `revalidatePath('/settings')` so the server re-renders last4 and the date. On error, also clear the input and ask the user to paste again, to avoid leaving the key in the DOM. Trade-off: this costs a re-paste on a validation error, but it is safer. Accept it.
6. **States per row.**
   - Chưa đặt (not set, no env): badge "Chưa có khoá — AI tắt" with an icon. Controls: input and "Lưu khoá".
   - Đã lưu qua giao diện: "Đã lưu — kết thúc bằng ••••1234 · lưu ngày 10/11/2026" (last4 visible as text, dots decorative `aria-hidden`). Controls: "Thay khoá" (reveals the input row) and "Xóa" (destructive, secondary style).
   - Đang dùng khoá môi trường (env fallback, no UI key): "Đang dùng khoá từ máy chủ (dự phòng)". Show NO last4 and no date, so env value details are not leaked. Controls: input and "Lưu khoá" (a UI key will take precedence). No delete.
   - UI key set and env also present: add a note "Khoá này được ưu tiên hơn khoá môi trường". After delete, show "quay về khoá môi trường" if env exists, else "AI tắt". The server must supply a `hasEnvFallback` boolean for this.
   - Saving: button `disabled` plus "Đang lưu…", `aria-busy`.
   - Save error: inline `role="alert"` text-price-down, generic and fixed-string messages by code (format invalid, too long or short, "Không lưu được. Thử lại.", session expired). Never interpolate the input.
   - Deleting with confirm: use a native `<dialog>` or an inline two-step ("Xóa khoá Anthropic?" with "Xóa" and "Hủy" buttons) instead of adding a new dependency. Inline two-step is simplest and testable. Move focus to the confirm button, return focus to the row's "Xóa" or input on cancel. Warn that the AI feature stops if there is no env fallback. Include the provider name in the `aria-label`, as in HolidayCalendarCard.
   - Success: `role="status"` "Đã lưu khoá Anthropic" or "Đã xóa khoá Anthropic". Do not use the `?saved=1` banner, which belongs to the settings form.
7. **Vietnamese labels.** Card title "Khoá AI" (as in the ticket; the codebase elsewhere uses "Xóa", so choose one spelling form per label and stay consistent). Note: "Khoá được mã hóa trên máy chủ, không bao giờ hiển thị lại. Khoá lưu ở đây được ưu tiên hơn khoá cấu hình trên máy chủ." Buttons: Lưu khoá, Thay khoá, Xóa, Hủy. Labels: "Khoá API Anthropic", "Khoá API Google AI".
8. **Accessibility.** `<section aria-labelledby>`; every input has a `<label>`; errors are linked via `aria-describedby` and `aria-invalid`. Touch targets are `min-h-11`. Status is conveyed by text plus an icon (lucide Check, Ban, AlertTriangle), not color alone. Live regions are per row (`role="status"`/`alert`). Never `aria-label` or `title` the last4 or the key. Keep focus order: input, Lưu, Xóa. Disable the Save button when the input is empty.
9. **Server-only (R3/R6, AC1/AC3).** Save and delete actions in `settings/actions.ts` (or `ai-keys-actions.ts`): `requireUser()` first; a whitelist-validated provider enum (never a client-provided secret name or Vault id); `trim()` then validate (no whitespace or newlines, length bounds, per-provider prefix hint only as a soft check); write via a service_role helper in `server/`, covered by the r3-guard. Return only a status code or message. Never log or `console.error` the FormData, the error object (the Supabase error can contain parameters), or the key. Last4 and the date must be derived or stored server-side (a non-secret metadata column or the Vault `description`) so the page never has to decrypt the key just to render the card. The page must not call anything that returns the decrypted secret. `export const dynamic='force-dynamic'` is already set. No client component should import a server module that touches the Vault. Types passed as props must be the plain row type.
10. **Tests (AC7).** Component tests (as in settings.test.tsx): the password type and autocomplete attributes; the input is cleared after both success and error; the rendered HTML never contains the submitted key (assert via `container.innerHTML` and the action's return); each of the 4 states renders correctly; delete requires confirmation; the env state shows no last4.

## Risks
- Nesting this card inside `SettingsForm`'s `<form>` would create invalid nested forms or let "Hủy" reset it. Keep it outside.
- Copying the settings `values` echo pattern would leak the key back in action state (violates AC1).
- A React 19 `<form action>` auto-resets uncontrolled inputs only on success, so clear explicitly in the error path as well.
- Browser or password-manager autofill and saved-password prompts: `autoComplete="new-password"` mitigates but cannot fully prevent them. Never put the key in a URL or query param.
- The key is in the DOM and in the React state briefly between paste and submit; unavoidable, so keep that window short.
- Next.js server-action error serialization and request logging in dev can expose the form payload; make sure no logger prints it, and that the Cloudflare Tunnel or proxy access logs do not record bodies (flag to the security auditor).
- Showing env-key presence/last4 would leak secrets; show presence only.

## Open questions
1. Delete confirm: native `<dialog>`, inline two-step, or add an AlertDialog primitive? (I recommend inline two-step; no new dependency, since R7/stack is unchanged.)
2. Keep the user on the same row for the success message, or redirect to `/settings?keysaved=...`? (I recommend revalidate plus an inline status; no redirect.)
3. Is a "test key" (live provider ping) button wanted? It costs money and egress; I recommend omitting it from this ticket (R7) and listing it as a follow-up.
4. Where do last4 and savedAt live (a metadata table or the Vault description)? That is for the db/architecture consults; the UI only needs `{status, last4, savedAt, hasEnvFallback}` per provider.
5. Spelling "Khoá" (ticket) versus "Khóa" (existing codebase uses "Xóa", "Hủy"): pick one for consistency.
