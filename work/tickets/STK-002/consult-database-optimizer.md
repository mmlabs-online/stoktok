# consult-database-optimizer — STK-002

**Findings**
- The spec §5 says holdings and P&L are derived, never stored as editable balances. `lots` is listed as a table, with `quantity_remaining`, `cost_per_share` and `sellable_from`. That makes `lots` a materialized cache of replaying `transactions` + `corporate_actions`. It is not a source of truth.
- `lots.quantity_remaining` and `sellable_from` depend on the as-of date and on corporate actions, so storing them risks drift. Corporate actions are the "most common source of P&L drift" (spec §2.1).
- `corporate_actions` has only `ratio/amount` and `applied`. The spec has no ex-date or payment date, and no separate fields for cash versus stock ratio. A stock dividend needs an effective date to order it against trades. `record_date` alone is ambiguous: cost basis and quantity change on the ex-date, and cash arrives on the payment date.
- The spec lists no `side` enum values, no `exchange` on transactions, and no quantity/price types. `sellable_from` needs settlement days and a trading calendar. Pure core can't know holidays unless a calendar is injected.

**Recommendations**
1. **Lots are derived in core.** Expose `buildLots(txs, actions, settings, asOf)`. It returns lots with status computed at call time and does not mutate input. Treat the DB `lots` table as an optional persisted snapshot, to be filled later by a rebuild function. Do not make `lots` an input to the core. Ledger replay from the transactions is the contract (spec §5 line 174).
2. **Mirror DB column shapes in core input types**, using camelCase in core and a snake_case mapper in the repository layer later (AC "integer VND", R2):
   - `Transaction { id: string; tradeDate: string /* 'YYYY-MM-DD', VN local, not a Date/timestamp */; symbol: string; side: 'buy'|'sell'; quantity: number /* int shares */; price: number /* int VND per share */; fee: number /* int VND, total for the trade */; tax: number /* int VND, total */; }`.
   - Use `bigint` columns or `integer` columns. A single trade value stays under 2^31 only for small trades (VND values reach billions), so the DB should use `bigint` for fee, tax and any total. Core should use JS `number` (safe up to 2^53) and assert `Number.isSafeInteger`. Flag this for the DB ticket: use `bigint` for money, but `integer` is fine for `quantity` and `price`.
   - `id` should be an opaque string in core, because the DB can use uuid or bigint. Core must not generate ids. Tie-breaking at equal dates needs a stable `seq` or `createdAt`; add `seq: number` (or order by `(tradeDate, id)` with the rule documented). Same-day buy and sell ordering matters for FIFO.
   - Persist `fee` and `tax` on the transaction when it is entered (user-editable actual from the broker). Core takes them as inputs and uses settings (`feeRate`, `sellTaxRate`) only to compute defaults via one exported function `estimateFees()`. Rounding is defined once: round half up to integer VND, in one module.
3. **Lot output shape maps 1:1 to the spec `lots` columns**: `{ id: string /* deterministic: 'lot:'+buyTransactionId (+ split suffix if needed) */; symbol; buyTransactionId; quantityOriginal; quantityRemaining; costPerShare; sellableFrom: string; status: 'pending'|'sellable'|'closed' }`. Deterministic ids let a future persisted snapshot upsert without reshaping. `costPerShare` as an integer is lossy: fee allocation and stock-dividend dilution produce fractions. Recommend the lot carry `costTotalRemaining` (integer VND) as the authoritative value, with `costPerShare` as derived (rounded). Average cost = sum of cost totals / quantity. This avoids cumulative rounding error, and the DB column can store either.
4. **Corporate action input**: `CorporateAction { id; symbol; type: 'cash_dividend'|'stock_dividend'|'rights_issue'; exDate: string; payDate?: string; amountPerShare?: number /* int VND */; stockRatio?: {num: number; den: number} }`. Recommend the DB ticket store `ex_date` (and `pay_date`) alongside `record_date`, and split `ratio/amount` into `amount_per_share bigint` and `ratio_num`/`ratio_den int`. Keep `applied` out of core. Core should be pure, so "applied" is an ops/UI concern, not a replay input. Rights issue is out of scope for STK-002 per the AC (cash and stock only). Make the type a discriminated union so adding rights later is non-breaking.
5. **Corporate-action semantics to document in the plan.**
   - Cash dividend: cost basis unchanged, quantity unchanged, and the cash is reported as `dividendIncome` separately from realized P&L. Quantity eligible is the holding at the close of the record date or as of the ex-date.
   - Stock dividend: lot quantity increases by `floor(qty * num/den)`, with fractions dropped. Cost total is unchanged, so the per-share cost falls. The new shares inherit the original lot's `sellableFrom` (document as an assumption, since in reality new shares have their own listing delay; flag to Ming).
6. **Sell consumption**: FIFO by lot buy date, ordered by `(tradeDate, seq)`, only over sellable lots, as of the sell's trade date. Vietnamese tax reporting generally treats cost as average/FIFO, so state the assumption and flag it to Ming (the AC already requires this). Make the method a named `LotMethod` parameter so it can change later.
7. **Result types for later persistence.** Make the realized-P&L entries per sell: `{ sellTransactionId; lotId; quantity; proceedsNet; costBasis; realizedPnl }`. They are derivable and let a DB ticket store or verify them without redesign. Oversell returns a typed error: `OversellError { symbol; requested; sellable; asOf }`. The core should return a `Result` or throw a class, but don't rely on strings.
8. **Time**: dates are plain `'YYYY-MM-DD'` strings in Asia/Ho_Chi_Minh, and the DB columns should be `date`, not `timestamptz`. Settlement uses an injected `addTradingDays(date, n, calendar)` with a default weekday-only calendar. Holidays come from config (R5).
9. **DB hints for the future ticket**: unique `(source, import_batch_id, external_ref)` for import idempotency; check constraints `quantity > 0`, `price >= 0`, `fee >= 0`, `tax >= 0`; index `(symbol, trade_date, id)` on `transactions`; index on the `lots` FK `buy_transaction_id`; RLS single-user.

**Risks**
- Storing `quantity_remaining` as editable state contradicts the spec rule against stored balances, and drifts when a backdated transaction is edited. Mitigation: rebuild from scratch (idempotent replay) is the only write path.
- Integer overflow in a Postgres `integer` money column for large trades (more than about 2.1 billion VND). Use `bigint`.
- Per-share rounding of fees gives errors in aggregate P&L. Allocate at the trade total level, and keep per-lot cost totals as integers using largest-remainder allocation when a buy is split across partial sells.
- Backdated or edited transactions that cause a retroactive oversell, which would change the replay result of later sells. The core must replay from the start and report the first violating transaction.
- Same-day ordering (buy then sell on the same date where T+2 means the sell can't use the lot) is handled by the sellable rule, but equal-date ordering for buys needs a deterministic tie-break.

**Open questions**
1. Does Ming's TCBS cost-basis method match FIFO or average cost? (Needed for the AC "documented method".)
2. For stock dividends, do the new shares become immediately sellable, or after the listing date? The plan will assume inheriting the parent lot's `sellableFrom` unless told otherwise.
3. Should cash dividends be recorded into the ledger as an income entry (needs a place in the schema, such as a `cash_events` table or an `assets` cash adjustment), or only computed in core output? Recommend computed-only for STK-002.
4. Is `fee`/`tax` entered per transaction (actuals) or always computed from settings? Recommend actuals when present and computed otherwise.
5. Odd-lot sells: allowed in the ledger (core shouldn't enforce the 100-share board lot on the ledger; only suggestions round to lots).
